# Звіт

Тестове завдання: сервіс лояльності для закладів на Syrve.
Репозиторій: https://github.com/hrezolit83/syrve-loyalty

---

## Що зроблено

Усі обов'язкові функції О1–О6 і дві додаткові — Д1 (історія операцій) і Д2 (список гостей).

| № | Функція | Стан |
|---|---|---|
| О1 | Підключення до Syrve: токен, організація, програма | зроблено |
| О2 | Реєстрація гостя в Telegram без дублів | зроблено |
| О3 | Картка, QR-код і баланс у боті | зроблено |
| О4 | Панель адміністратора з входом і пошуком гостя | зроблено |
| О5 | Ручне нарахування і списання з журналом | зроблено |
| О6 | Сповіщення про зміну балансу без дублів | зроблено |
| Д1 | Історія операцій у боті й у панелі | зроблено |
| Д2 | Список гостей із пошуком, сортуванням, пагінацією | зроблено |

Технічні вимоги ТЗ: запуск однією командою `docker compose up --build` — так; зміни схеми лише міграціями — сім міграцій у `api/prisma/migrations`; запуск без доступу до Syrve — `SYRVE_MODE=mock`.

**Чому вибрані саме Д1 і Д2.** Д1 закриває питання, яке в гостя виникає першим після «скільки в мене бонусів» — «за що саме нарахували». Воно ж потрібне адміністратору: коли гість сперечається про баланс, у панелі видно всі зміни з боку Syrve, включно з касою й кабінетом, а не лише операції нашої панелі. Д2 — те, без чого панель незручна в роботі: шукати гостя лише за повним телефоном незручно, коли треба просто подивитися, хто реєструвався. Обидві спираються на вже готові частини (клієнт Syrve, власна таблиця гостей) і не вимагали нового стеку — тому на них залишився час після того, як О1–О6 стали надійними.

## Що перевірено і як

### Автоматичні перевірки

Замість юніт-тестів — два скрипти, які проходять сценарії наскрізь по справжній базі, чергах і воркерах. Запускаються з папки `api/`.

**`node scripts/check-syrve-real.mjs`** — робота з живим Syrve (`SYRVE_MODE=real`):

| Перевірка | Результат |
|---|---|
| Невідомий телефон → `null`, а не виняток | OK |
| Реєстрація: картка 10 цифр, базова лінія `lastRevision` | OK (`5203529989`) |
| Повторна реєстрація: той самий гість і картка в Syrve | OK |
| Баланс читається з гаманця нашої програми | OK |
| Нарахування 50 змінює баланс | OK (0 → 50) |
| Списання понад баланс відхиляє наша перевірка | OK (409) |
| Списання 20 у межах балансу | OK (50 → 30) |
| Синхронізація записує лише транзакції нашої програми | OK (2 записи) |
| Типи класифіковано правильно, `SetGuestCategory` відфільтровано | OK |
| Повторна синхронізація: 0 нових | OK |

Скрипт створює тестового гостя в організації, повертає його баланс до нуля й прибирає свої записи з бази.

**`node scripts/check-notifications.mjs`** — надійність О6 (мок-режим, підміняється лише відправка в Telegram; поллер, черги, база й воркери справжні):

| Перевірка | Результат |
|---|---|
| Операція з панелі → рівно одне повідомлення | OK |
| Два додаткові проходи поллера → без дублів | OK |
| Перезапуск воркерів → без дублів | OK |
| Зміна з кабінету Syrve (тип `7 RefillWallet`) → одне повідомлення | OK |
| Напрямок правильний (нараховано) | OK |
| Невідомий тип із `sum ≠ 0` → сповіщення | OK |
| Напрямок за знаком суми, а не за назвою типу | OK (`−7` → «Списано») |
| `SetGuestCategory` → сповіщення немає, але курсор зсунуто | OK |
| Списання через сервіс → «Списано» | OK |
| `403` (бота заблокували) → гість позначений | OK |
| `403` → задача знята з першої спроби, без ретраїв | OK |
| Курсор дорівнює останній ревізії | OK |
| Усі доставлені транзакції мають `notifiedAt` | OK |

### Перевірки, проведені окремо

**Гонка при списанні.** Три паралельні запити на списання по 50 з балансу 110 → `200 / 409 / 200`, баланс 10. Без блокування на рівні гостя всі три пройшли б перевірку й баланс став би −40.

**Ліміт спроб входу.** 12 запитів на вхід із неправильним паролем: перші 9 — `401`, далі `429`. За nginx у Docker лімітер лишається персональним: у логу API видно адресу клієнта (`172.19.0.1`), а не контейнера nginx — тобто `trust proxy` і `X-Forwarded-For` налаштовані правильно.

**Авторизація панелі.** Без входу `/api/admin/*` → `401`; неправильний пароль і невідомий логін дають однаковий текст (щоб перебором не з'ясовувати існуючі логіни); cookie з JWT має `HttpOnly`; після «Вийти» сторінки знову недоступні.

**Валідація.** Сума 0, сума з трьома знаками після коми, причина з двох символів, телефон «123» — усі дають `400` з українськими повідомленнями по кожному полю.

**Розклад поллера.** З `POLL_INTERVAL_SEC=5` воркер зробив 5 проходів за 22 секунди. У Redis мітки повторюваної задачі йдуть із кроком рівно 30 с при стандартному налаштуванні.

**Запуск із нуля.** `docker compose down -v` (volumes стерто) → `docker compose up --build`: сім міграцій накатилися автоматично, сід створив адміністратора, воркер підняв бота й поллер, панель відповіла на `:8080`, `/api/health` → `database: up`, `/api/health/syrve` → організація й програма знайдені. Повний цикл панелі через nginx: вхід → пошук гостя → нарахування → журнал → списання.

**Секрети.** Перед кожним комітом — пошук значення `apiLogin`, токена бота й пароля адміністратора в `git diff`. Жодного влучання. Ключ не потрапляє ні в логи (перевірено пошуком по файлах логів), ні у відповіді API, ні у зразки в `docs/api-samples/`. Поле `apiClientLogin`, яке Syrve повертає в транзакціях, додано в `redact` логера.

**Формат чисел і текстів.** `Intl.NumberFormat('uk-UA')` у боті й панелі: `150`, `12,50`, `1 250,75`. Відмінки: «1 бонус», «2 бонуси», «5 бонусів», «12,50 бонуса»; «1 операція», «2 операції», «5 операцій». Перевірено й те, що UTF-8 проходить наскрізь від запиту до бази (перші перевірки через консоль Windows давали пошкоджений текст — виявилося, що псує саме консоль, а не сервіс).

## Що не зроблено і чому

**Д3 — Telegram Mini App.** Не робився. Бот покриває ті самі функції (картка, QR, баланс, історія), а Mini App вимагав би перевірки підпису `initData` на сервері й публічного HTTPS. Пріоритет був на надійності О1–О6: сповіщення без дублів і захист від мінусового балансу важливіші за приємніший інтерфейс тих самих даних.

**Д8 — картка в Apple/Google Wallet.** Не робилася. Потребує сертифікатів Apple Developer і налаштування Google Wallet API — це окрема історія з доступами, яку не закрити в межах завдання.

**Д9 — статистика.** Не робилася. Кількість гостей і нових реєстрацій можна порахувати з нашої БД, але суми нарахувань і списань по закладу живуть у Syrve, і для правдивих чисел потрібен звіт за організацією, а не обхід гостей. Робити неточну статистику не хотілося.

**Д10 — ролі та журнал дій.** Не робилося. Журнал уже записує, який адміністратор виконав операцію, тож залишилася перевірка прав; але це вимагає таблиці ролей і рішень про те, що саме заборонено менеджеру — питання до замовника, а не вгадування.

**Автотестів немає.** Свідомий вибір на один день: два скрипти перевірки проходять саме ті сценарії, які ламаються (дублі сповіщень, гонки, формати Syrve), і їх видно в роботі. Юніт-тести на нормалізацію телефону, класифікацію типів транзакцій і розбір помилок Syrve — перше, що варто додати далі.

**Живий Telegram перевірявся руками, не автоматично.** Відправка в Telegram у скрипті перевірки підміняється, бо автоматизувати натискання кнопок у клієнті Telegram у межах завдання невиправдано. Сам бот перевірений руками (див. «Ручна перевірка»).

## Відомі обмеження

**Поллер масштабується як O(кількість гостей).** `customer/transactions/by_revision` вимагає `customerId`, тому кожен прохід робить мінімум один запит до Syrve на кожного гостя. На сотні гостей і 30-секундному інтервалі це тисячі запитів на годину. Шляхи далі описані в `ARCHITECTURE.md`: різна частота для активних і «спящих» гостей, звіт за організацією замість обходу.

**Історія операцій гортає всі транзакції гостя.** «Останні 10» збираються з повного списку, бо `by_revision` віддає від заданої ревізії за зростанням. Для десятків операцій на гостя нормально; на тисячах потрібен `transactions/by_date`. Цей метод існує, але перевірити його на реальних даних тестової організації не вдалося, тому залишено те, що точно працює.

**Один адміністратор без ролей.** Усі, хто ввійшов, мають однакові права.

**`lastRevision` на кожного гостя.** Якщо гостя видалити з нашої БД і зареєструвати заново, базова лінія стане поточною — старі операції сповіщеннями не прилетять. Це бажана поведінка, але варто знати: історія в боті (Д1) при цьому лишається повною, бо читається з Syrve.

**Сповіщення залежать від того, що гість не заблокував бота.** При `403` сервіс позначає гостя й перестає йому писати. Якщо гість потім розблокує бота, позначка знімається тільки після нового `/start` — автоматичного повторного спроба немає.

**Syrve дозволяє мінусовий баланс.** Захист лише в нашому сервісі. Якщо баланс зроблять мінусовим безпосередньо в кабінеті Syrve, сервіс це покаже як є й надішле гостю сповіщення — своїх обмежень на дані Syrve ми не накладаємо.

## Побічні дії в тестовій організації

Усе, що сервіс і перевірки зробили в наданій організації «Демо В.С.» — відкрито:

- **Створено двох тестових гостей:**
  - `+380991000001` «Тестовий Гість (розвідка API)» — створений скриптом розвідки `scripts/explore.js --with-customer`, коли збиралися зразки відповідей;
  - `+380991000002` «Перевірка Етапу3» — створюється скриптом `api/scripts/check-syrve-real.mjs`.
  Обом видано картки (10 цифр, `track = number`) і додано в програму «Бонусная программа в зале и в доставке».
- **Баланси повернуто до нуля.** Під час перевірки, чи Syrve відхиляє списання понад баланс, баланс гостя `+380991000001` пішов у **−999 993**. Це був навмисний тест межі; одразу після нього баланс повернуто нарахуванням тієї ж суми — на момент здачі він **0**. Баланс другого тестового гостя теж повернуто до нуля.
- **Реальний гість.** Гість, зареєстрований через бота під час ручної перевірки, лишився в Syrve з карткою й історією операцій — це нормальний результат роботи сервісу, не сміття.
- **Налаштування програм лояльності не змінювалися.** Жодних правок у кабінеті Syrve Loyalty зроблено не було, як і просили в ТЗ.
- **Метод `POST /api/1/access_token` позначений у документації як deprecated.** Використовується саме він, бо ТЗ видає `apiLogin`, а цей спосіб авторизації працює через v1. Якщо для видаваних ключів з'явиться новий метод — міграція зводиться до одного місця в `api/src/services/syrve/realClient.js`.
- **Програму вибрано явно.** В організації чотири активні програми лояльності. Сервіс працює з «Бонусная программа в зале и в доставке» (`SYRVE_PROGRAM_ID` у `.env`). Якщо мала бути інша — зміна одного рядка без правок коду.
