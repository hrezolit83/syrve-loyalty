# План розробки

Складено на старті, до написання коду. Відхилення від плану фіксуються в розділі «Зміни плану» внизу.

## Ключові рішення

- **Баланс, картки, транзакції живуть у Syrve.** Сервіс їх не дублює, а читає через Syrve Cloud API. Локально зберігається лише те, чого в Syrve немає: зв'язок Telegram ↔ гість, адміністратори, журнал ручних операцій, стан синхронізації транзакцій.
- **Сповіщення (О6) через polling.** Syrve не надсилає вебхуків про зміну балансу, тому фонова задача періодично викликає `customer/transactions/by_revision`. Метод працює для одного гостя (`customerId` обов'язковий), тому курсор `revision` зберігається для кожного гостя окремо.
- **Захист від дублів сповіщень:** унікальний ключ `transactionId` у таблиці оброблених транзакцій + `jobId = transactionId` у черзі BullMQ. Курсор оновлюється в одній транзакції БД із записом оброблених — після перезапуску нічого не дублюється й не губиться.
- **Токен Syrve** кешується, оновлюється за 5 хв до закінчення (живе 1 год) і при відповіді 401.
- **Тестовий режим** `SYRVE_MODE=mock` — фейковий клієнт із тим самим інтерфейсом, щоб сервіс можна було показати без доступу до Syrve.
- **Секрети** лише в `.env` (репозиторій публічний).

## Стек

| Частина | Технологія | Чому |
|---|---|---|
| API | Node.js, Express 5, Joi | Перевірена структура з попереднього проєкту, швидкий старт |
| БД | PostgreSQL + Prisma | Реляційні зв'язки, міграції у Git |

| Адмін-панель | React + Vite + TypeScript | Типізація, швидка збірка |
| Запуск | Docker Compose | Увесь сервіс однією командою |

Розвідку відкладено, зразки відповідей зберуться пізніше одним запуском `scripts/explore.js`. Щоб не стояти, етапи 1–2 робимо на `SYRVE_MODE=mock` — мок-клієнт будується за формою відповідей із ТЗ.
- 07.11: `docker-compose.yml` робимо у два заходи: на етапі 1 лише `postgres` + `redis` (щоб працювали міграції й локальна розробка), повний набір сервісів — на етапі 6, як у плані.
- 07.11: етап 1 — `revision` і `lastRevision` зроблені `BigInt`, а не `Int`: у Syrve revision — 64-бітне число, а `Int` у PostgreSQL обмежений 2 147 483 647, і переповнення зламало б поллер О6 вже на реальних даних.
- 07.11: порти локального стеку зсунуті (API 3001, PostgreSQL 5433, Redis 6380) — стандартні 3000/5432/6379 на машині розробника зайняті іншим проєктом. У `.env.example` значення порожні, тож на чистій машині працюють дефолти 3000/5432/6379.
- 07.11: npm 11 за замовчуванням блокує install-скрипти, тому в `api/package.json` з'явився розділ `allowScripts` для `prisma`, `@prisma/client`, `@prisma/engines`, `bcrypt`, `msgpackr-extract` — без нього не виконується `prisma generate` і не збирається нативний `bcrypt`.
- 07.11 20:30: виданий apiLogin повертає 401 (not authorized), повідомив роботодавця. Розробка йде в mock-режимі за схемами OpenAPI.- 07.11: етап 2 — мок-режим зберігає дані не в пам'яті процесу, а в окремих таблицях `mock_customers` / `mock_transactions`. Номер підтверджує сам Telegram (`contact.user_id === from.id`), тож це той самий власник; історія операцій і `processed_transactions` гостя зберігаються.
